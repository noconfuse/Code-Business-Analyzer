# 代码质量评估指标体系

本评估框架锚定 **ISO/IEC 25010** 软件质量模型国际标准。按照以下维度逐项评估，给出 1-10 分评分、置信度标签 [高]/[中]/[低]、具体说明。

## 1. 架构设计 (Architecture & Design)

### 1.1 整体架构
- 是否采用清晰的分层架构（如 MVC、Clean Architecture、DDD 等）
- 模块/包之间是否存在循环依赖
- 是否遵循关注点分离原则（Separation of Concerns）
- 架构风格是否与项目类型匹配（微服务 vs 单体 vs Serverless 等）

### 1.2 设计模式使用
- 是否合理使用设计模式解决常见问题
- 是否存在过度设计（Over-engineering）或设计不足
- 关键设计决策是否有文档说明（ADR - Architecture Decision Records）

### 1.3 可扩展性
- 是否预留了合理的扩展点（接口、插件机制、策略模式等）
- 添加新功能是否需要大量修改现有代码（开闭原则）
- 是否支持水平/垂直扩展

## 2. 代码规范与风格 (Code Standards & Style)

### 2.1 一致性
- 命名规范是否统一（变量、函数、类、文件命名风格）
- 代码风格是否一致（缩进、括号、分号、空行等）
- 是否配置了 Lint 工具（ESLint、Prettier、pylint、golangci-lint 等）

### 2.2 可读性
- 函数/方法长度是否合理（建议单函数不超过 50 行）
- 嵌套层级是否过深（建议不超过 4 层）
- 变量命名是否语义清晰、自解释
- 注释是否充分且有价值（解释 Why 而非 What）

### 2.3 代码组织
- 文件结构是否清晰合理
- 单文件职责是否单一
- 导入/依赖管理是否规范

## 3. 安全性 (Security)

### 3.1 常见安全漏洞
- 输入验证：是否对所有外部输入进行验证和清理
- SQL 注入：是否使用参数化查询或 ORM
- XSS/CSRF：前端是否有防护措施
- 认证与授权：是否实现安全的身份验证和访问控制
- 敏感数据：密码是否加密存储、密钥是否硬编码

### 3.2 依赖安全
- 第三方依赖是否有已知漏洞（检查 CVE）
- 依赖版本是否过时
- 是否锁定依赖版本（lock 文件）

### 3.3 安全最佳实践
- 是否使用 HTTPS
- 是否实施了 CORS 策略
- 错误信息是否泄露敏感数据
- 是否有速率限制和防护机制

## 4. 性能 (Performance)

### 4.1 算法效率
- 关键路径算法的时间复杂度是否合理
- 是否存在 O(n²) 或更高复杂度的操作
- 数据结构选择是否恰当

### 4.2 资源管理
- 数据库查询是否优化（索引、N+1 问题、懒加载）
- 内存使用是否合理（是否有内存泄漏风险）
- 是否存在资源未释放问题（文件句柄、连接池等）
- 是否实现了缓存策略

### 4.3 前端性能（如适用）
- 是否有代码分割和懒加载
- 静态资源是否压缩和优化
- 是否使用 CDN
- 首屏加载性能是否优化

## 5. 可维护性 (Maintainability)

### 5.1 模块化
- 模块间耦合度是否低（Loose Coupling）
- 模块内聚度是否高（High Cohesion）
- 是否遵循 DRY 原则（减少重复代码）
- 是否遵循 SOLID 原则

### 5.2 测试覆盖
- 是否有单元测试、集成测试、端到端测试
- 测试覆盖率是否达到合理水平（建议 > 70%）
- 测试质量是否高（是否测试了边界条件和异常路径）
- 是否使用 CI/CD 自动化测试

### 5.3 文档完整性
- 是否有 README 和项目文档
- API 是否有文档（Swagger/OpenAPI 等）
- 代码内注释是否有价值
- 是否有部署文档和运维手册

### 5.4 可观测性
- 是否有日志记录（Log）
- 是否有监控指标（Metrics）
- 是否有链路追踪（Tracing）
- 是否有告警机制

## 6. 技术债务 (Technical Debt)

### 6.1 代码异味
- 是否有大量 TODO/FIXME/HACK 注释
- 是否有被注释掉的代码块
- 是否有超长函数和超长文件
- 是否有魔法数字和硬编码字符串

### 6.2 技术选型
- 使用的技术栈是否仍然活跃和受支持
- 是否使用了已废弃的 API 或框架
- 版本升级路径是否清晰

### 6.3 重构需求
- 哪些模块需要优先重构
- 重构的优先级和风险评估
- 建议的重构策略

## 7. 竞品代码对标分析 (Competitor Code Benchmarking)

在识别出 2-3 个技术路线相近的开源竞品后，从代码层面进行横向对比。此分析为同质化判断提供技术侧输入。

### 7.1 项目规模对标

| 指标 | 本项目 | 竞品A | 竞品B |
|------|--------|-------|-------|
| 总代码行数 | X | Y | Z |
| 主要语言及占比 | Lang (X%) | Lang (Y%) | Lang (Z%) |
| 文件数量 | X | Y | Z |
| 核心模块数 | X | Y | Z |

### 7.2 技术栈对标

- **后端框架**：本项目 vs 竞品的技术选型差异
- **数据库**：数据存储方案的异同
- **部署方式**：Docker / K8s / Serverless / 裸机
- **第三方依赖**：依赖数量、关键依赖的重叠度

### 7.3 工程成熟度对标

| 指标 | 本项目 | 竞品A | 竞品B |
|------|--------|-------|-------|
| 是否有 CI/CD | ✓ / ✗ | ✓ / ✗ | ✓ / ✗ |
| 测试覆盖率（估算） | X% | Y% | Z% |
| 是否有文档站点 | ✓ / ✗ | ✓ / ✗ | ✓ / ✗ |
| 是否有贡献指南 | ✓ / ✗ | ✓ / ✗ | ✓ / ✗ |
| 代码规范工具 | ESLint/... | ... | ... |
| Docker 支持 | ✓ / ✗ | ✓ / ✗ | ✓ / ✗ |

### 7.4 社区活跃度对标

| 指标 | 本项目 | 竞品A | 竞品B |
|------|--------|-------|-------|
| Stars | X | Y | Z |
| 近期提交频率 | X/周 | Y/周 | Z/周 |
| Contributors 数量 | X | Y | Z |
| Issues 响应速度 | X | Y | Z |
| Release 频率 | X | Y | Z |

### 7.5 代码架构同质化判断

通过对比代码结构和技术选型，判断本项目与竞品在技术实现层面的差异化程度：

- **高同质化**：与竞品使用相同的框架、相同的架构模式、相同的数据库方案，代码组织方式高度相似。意味着技术层面几乎没有壁垒。
- **中同质化**：部分技术选型不同，或有明显的架构设计差异，但整体思路相似。
- **低同质化**：使用了独特的技术方案或架构设计，与竞品有显著差异。这可能构成技术壁垒。

此判断结果为报告第五章"竞品与护城河"中同质化指数的"技术路线重叠度"维度提供依据。

## 评分标准

每个维度评分 1-10 分：
- **9-10 分**：优秀，行业标杆水平
- **7-8 分**：良好，有少量改进空间
- **5-6 分**：及格，存在明显需要改进的地方
- **3-4 分**：较差，存在较大风险
- **1-2 分**：极差，需要紧急处理

## 输出要求

### 代码质量评估输出
对每个维度：
1. 给出具体评分（1-10），附置信度标签 [高]/[中]/[低]
2. 列出发现的具体问题（附代码位置）
3. 给出改进建议
4. 标注优先级（高/中/低）

**代码位置引用强制规范**：
- 每个评分维度必须引用至少 1 个具体文件路径（如 `src/web/contexts/dataset/domain/capabilities.py`）或函数名（如 `build_dataset_capabilities()`）作为评分依据
- 引用格式：在评分说明中用反引号包裹路径，如："架构设计 7/10 — `src/web/contexts/dataset/domain/capabilities.py` 的能力表设计体现了 DDD 思想，按任务类型动态构建操作权限"
- 引用深度要求：至少到函数/类级别。禁止只写目录名（如 "src/web/contexts/" ），必须精确到文件或更细粒度
- 每个维度至少 1 个引用，推荐 2-3 个（正面证据 + 负面证据各一）
- 如代码库 > 500 文件且无法逐一阅读，至少覆盖核心入口文件（main.py / app.py）、领域模型、关键基础设施层各 1 个

**禁止的表述**：
- "代码质量良好" — 必须说明好在哪里、依据什么
- "架构设计合理" — 必须引用具体的架构决策和代码体现
- "存在技术债务" — 必须指出具体债务位置（哪个文件、什么问题）
- "安全性需要加强" — 必须指出具体的攻击面或缺失的防护

最终给出代码质量综合评分（加权平均）和雷达图数据。

### 竞品代码对标输出
在 Phase 5 中识别竞品后，执行以下对标分析（此内容延迟到 Phase 5 执行，Phase 2 不处理）：
1. 获取竞品 GitHub 仓库的公开数据（Stars、提交频率、技术栈等）— 必须通过搜索验证，不得凭记忆填写
2. 按照 Section 7 的框架生成竞品代码对标表
3. 给出"技术路线同质化判断"（高/中/低），为报告第五章的同质化指数中"技术路线重叠度"维度提供依据
