# 商业分析报告 — 分析细则

本文档定义各章节的分析深度和输出规范。章节结构、评分体系、方法论锚定见 SKILL.md。

---

## 01. 执行摘要

- **一句话定位**：3 句话以内，说清"解决什么问题、怎么解决、核心差异"
- **核心发现**：5 条，每条附带量化指标（如"代码质量 7.2/10 [高]"）
- 评分卡在第 2 章，不在此处重复
- **反冗余**：不在执行摘要中放置判定结果（GO/谨慎/NO-GO），判定仅在封面和第 7 章展示
- **与 SWOT 差异化**：执行摘要聚焦"对决策影响最大的发现"，SWOT 聚焦"结构性优劣势"，内容不得重叠

---

## 02. 项目概览

- **基本信息表**：所有字段从代码中提取，不存在则填 `"—"`
- **核心功能**：功能概述 1-2 句话 + 3 个标签
- **五维评分卡**：代码质量 / 赛道位置 / 差异化程度 / 商业潜力（第 5 维"团队/执行力"仅在雷达图）

---

## 03. 代码质量

锚定 ISO/IEC 25010。详见 `references/code_quality_metrics.md`。竞品代码对标内容来自 Phase 5。

输出：六维雷达图 + 维度评估表（含置信度标签）+ 竞品代码对标表 + Top 5 风险点。

### 代码锚定强制要求
- 每个维度评分必须引用至少 1 个具体文件路径或函数名作为证据
- 引用深度：至少到函数/类级别，不得只引用目录名
- 格式示例："架构设计 7/10 — 如 src/contexts/dataset/domain/capabilities.py 的能力表设计体现了 DDD 思想"
- 禁止空泛评价：不得出现"代码质量良好""架构设计合理"等无代码支撑的结论
- 如代码库 > 500 文件，至少覆盖 3 个核心模块的深度阅读

## 04. 市场与赛道

### 市场规模准则（TAM/SAM/SOM）
- 必须区分三层：TAM（总市场）/ SAM（可服务市场）/ SOM（可获取市场）
- SOM 基于项目可达渠道估算，禁止用 TAM 替代 SOM
- 增长率取 CAGR，标注时间范围（如 "2023-2028 CAGR"）
- 所有数字标注 [源N]

### 趋势风向量化阈值
- 强顺风：CAGR > 25% + 资本流入同比增长 + 政策利好
- 温和顺风：CAGR 15-25% 或资本流入正增长
- 中性：CAGR 5-15% 且资本流向不明
- 温和逆风：CAGR 0-5% 或资本撤离
- 强逆风：CAGR < 0% 或政策限制

### 赛道分析准则
- **阶段**：萌芽（资本未进入）→ 成长（CAGR > 20%）→ 成熟（CAGR 5-15%）→ 衰退（CAGR < 0%）
- **热度**：冷（< 5 个明显玩家）→ 热（5-20 个）→ 过热（> 20 个 + 融资泡沫）
- **集中度**：高（CR4 > 60%）→ 中（CR4 30-60%）→ 低（CR4 < 30%）
- 市场机会需指出"未被满足的需求"或"现有玩家做得不好的点"

## 05. 竞品与护城河

### 竞品选择准则
- 优先选直接竞品（解决相同问题）；无直接竞品选间接竞品（替代方案或上游工具）
- 至少 2 个，目标 3-4 个

### 同质化指数评分锚点
| 功能重叠度 (40%) | 技术路线重叠度 (30%) | 用户重叠度 (20%) | 商业模式重叠度 (10%) |
|:-:|:-:|:-:|:-:|
| 1-3: 功能几乎无交集 | 1-3: 完全不同的技术栈和架构范式 | 1-3: 目标用户群完全不同 | 1-3: 收费/分发方式完全不同 |
| 4-6: 部分功能重叠但各有侧重 | 4-6: 部分技术选型相同但整体路线不同 | 4-6: 用户群有交集但不是同一批人 | 4-6: 同属开源但盈利模式不同 |
| 7-10: 核心功能几乎一样 | 7-10: 框架/架构/数据库几乎一样 | 7-10: 争夺同一批用户 | 7-10: 商业模式完全相同 |

附加 Blue Ocean 判断：指数 ≥ 6 = 红海竞争；指数 ≤ 3 = 创造了新市场空间。

### 护城河评分锚点（Porter Five Forces）
六维各 1-10 分，本项目 + 最强竞品双线对比：
- **品牌壁垒**：1-3 无名 / 4-6 社区有认知度 / 7-10 行业标杆
- **网络效应**：1-3 单用户独立 / 4-6 用户间有协作价值 / 7-10 用户越多价值指数增长
- **数据飞轮**：1-3 无数据积累 / 4-6 使用越多效果越好 / 7-10 数据形成排他性壁垒
- **技术壁垒**：1-3 纯 CRUD / 4-6 有专有算法或架构 / 7-10 有专利或明显技术代差
- **先发优势**：1-3 后进入者 / 4-6 先进入但优势不明显 / 7-10 第一名且领先明显
- **合规壁垒**：1-3 无合规要求 / 4-6 需认证但可获取 / 7-10 许可证稀缺/不可复制

另需定性分析（不计入六维评分，写入护城河评价文本）：
- **替代品威胁**：是否存在完全不同的解决方案替代本项目
- **新进入者威胁**：进入门槛高低，大厂如果下场做的难度

### SWOT 准则
- 优势(S)：必须可验证（"DDD 分层架构降低模块耦合度 [代码可见]"，不是"代码写得好"）
- 劣势(W)：具体到"功能矩阵缺 X / 无 Docker 化 / 无 CI"
- 机会(O)：基于市场趋势的具体切入点
- 威胁(T)：具体到竞品或趋势拐点

## 06. 商业价值

### 价值类型识别（Step 0）

判断项目主价值类型（五类取 1-2 类为主）。主类型 = 项目最核心价值主张所属类别。

| 类型 | 识别信号 |
|------|---------|
| 先进工具 | 用户已有方案，项目让方案更快/更省/更强 |
| 普惠化 | 用户原来做不到，项目降低了门槛使之能做 |
| 信息差消除 | 项目核心是连接供需双方，不生产内容/商品本身 |
| 细分痛点 | 大公司看不上、通用工具覆盖不了的尖锐场景 |
| 趋势载体 | 项目是某个不可逆社会变迁的载体实现 |

### 各类型评估准则

#### 先进工具
- 效率提升必须量化（"集成时间从 2 周 → 7 行代码"），不得用"大幅提升"替代
- 切换动力判断：迁移成本 > 效率收益时标注"切换阻力高"
- 技术壁垒：明确效率优势来源（算法/架构/数据/规模），标注可复制性

#### 普惠化
- 新用户群体规模必须量化或估算区间
- 替代品分析：明确用户"不做"的成本 vs 用本项目的成本
- 质量可持续性：如降低门槛导致产出质量不可控，标注为风险

#### 信息差消除
- 冷启动策略必须具体（"先签 X 侧 → 再拉 Y 侧"），不得只写"通过运营解决"
- 双边流动性：如有数据引用供需比和 N 日留存；无数据标注"待验证"
- 网络效应强度：明确"用户增加 → 价值增加"的传导链路

#### 细分痛点
- 痛点验证：引用搜索量/论坛讨论/GitHub Issue 作为外部证据，不得只凭主观判断
- 缝隙市场容量：目标用户 × 付费意愿 = 估算 ARR
- 大厂威胁：分析这个缝隙是否在大公司雷达上

#### 趋势载体
- 趋势不可逆性：列出驱动趋势的外部条件，逐条判断是否会倒退
- 载体 vs 过渡形态：项目是趋势的终点形态还是中间态？如果是中间态，什么条件会替代它
- 窗口期：估算先发优势的剩余时间
- 终局路径：独立成长 or 被收购？如被收购，最可能的买家和理由

### 通用评估（所有类型必填）

- **市场规模**（TAM/SAM/SOM）：三层漏斗，SOM 基于可达渠道估算
- **商业模式**（Business Model Canvas）：9 构件逐项分析
- **创新类型**（Christensen）：延续性 or 破坏性
- **采用阶段**（Crossing the Chasm）
- **PMF 验证状态**（Lean Startup）

### 投资价值评级（类型感知）
评级标准根据主价值类型调整权重：

| 评级 | 先进工具 | 普惠化 | 信息差消除 | 细分痛点 | 趋势载体 |
|:-:|------|------|------|------|------|
| A | 效率 ≥ 10x + 壁垒高 + SOM > $50M | 新用户群 > 百万 + 质量可持续 | 双边自转 + 网络效应强 | 痛点经验证 + ARR 可达 $5M+ | 趋势不可逆 + 载体非过渡态 |
| B | 上述满足 2/3 | 上述满足 2/3 | 上述满足 2/3 | 上述满足 2/3 | 上述满足 1/2 + 窗口期充足 |
| C | 上述满足 1/3 | 上述满足 1/3 | 上述满足 1/3 | 上述满足 1/3 | 窗口期紧张或过渡态 |
| D | 均不满足 | 均不满足 | 均不满足 | 均不满足 | 趋势可逆 |

## 07. 投资决策

### 魔鬼代言人
判定前先写"为什么应该毙掉"3 条论点（附量化支撑），再写"为什么值得继续"3 条。最终判定必须回应反方论点——无法反驳时不得高于"谨慎"。

**质量要求**：
- 反方 3 条论点每条必须有具体数据或事实支撑，禁止"差异化不够"等空泛表述
- 正方 3 条论点每条必须有可验证的依据
- 禁止自我否定：反驳时不得出现"但这个论点没有证据""无法反驳"等自削弱表述。如果确实无法反驳，直接降低评级，不在正文中自认失败
- 判定必须回应反方："尽管存在 [反方论点 X]，但因为 [正方因素 Y]，判定为 Z"

### Kill Criteria 检查
逐条检查 K1-K6（见 SKILL.md），命中时自动降档并标注规则编号。

### 判定依据准则
- 每条依据提供 1 个量化支撑（"同质化指数 5.2/10"，不是"差异化不够"）
- "谨慎"判定必须附带转绿条件（"满足 X 条件后可调为 GO"）

### 决策矩阵定位
```
        赛道吸引力高
    ┌─────┴─────┐
    │ 谨慎   GO  │ ← 相对竞争力强
    │ NO-GO  谨慎 │ ← 相对竞争力弱
    └─────┬─────┘
        赛道吸引力低
```

### 行动建议质量要求
- **必须项目具体**：每条行动建议必须关联到项目的具体代码结构或功能模块。禁止"补测试""建社区"等适用于任何项目的泛泛建议
- **格式**："[具体模块/功能] → [具体行动] → [预期效果]"。例如："src/ 目录无测试文件 → 为 dataset/ 和 training/ 上下文补充单元测试 → 降低重构风险"
- **Impact/Effort 矩阵**：每个行动项按影响（1-5）和难度（1-5）标注：
  - 影响 ≥ 4 且 难度 ≤ 2：立即执行
  - 影响 ≥ 4 且 难度 ≥ 3：计划排期
  - 影响 ≤ 3 且 难度 ≤ 2：有余力时做
  - 影响 ≤ 3 且 难度 ≥ 3：暂不做
- **禁止万金油建议**：以下建议在任何报告中都适用，因此必须附带项目具体上下文才可使用：
  - "补充测试" → 必须说明哪些模块缺测试、缺什么类型的测试
  - "建立社区" → 必须说明当前社区状态、目标平台、具体运营动作
  - "探索商业化" → 必须说明基于什么信号判断有商业化机会

## 08. 未来方向

- **短期 (0-3月)**：可立即执行的具体任务，优先补短板。每项关联可验证里程碑（如"Docker 镜像发布""CI 覆盖率 > 70%"），禁止"优化性能""加强文档"等无法验收的表述
- **中期 (3-12月)**：产品升级和差异化深化
- **长期 (1-3年)**：战略方向和可能的 pivot
- **PMF 验证路径**（如 PMM 未验证）：定义最小验证实验和成功指标

### 风险与应对
至少覆盖：技术风险（技术债/依赖过时）、市场风险（巨头入场/需求转移）、合规风险（许可证/数据隐私）、竞争风险（竞品追赶）

## 附录: 数据溯源

### 可信度分级标准
- **A 级**：可交叉验证的权威数据（Gartner/IDC/年报/GitHub 公开数据/政府统计/交易所公告）
- **B 级**：有参考价值但精确度待验证（科技媒体如 TechCrunch/36Kr/行业白皮书/咨询公司报告）
- **C 级**：AI 推理，无外部数据支撑（代码质量评分、模型推断的市场判断）

每个外部数据引用需累计编号 [源1]、[源2]…，在溯源表中逐条对应。代码质量评分统一标注 C 级。
